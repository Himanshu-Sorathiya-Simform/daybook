# F15 Demo and seed data

16 Oct 2026 · @Himanshu

Daybook needs realistic data in two places.

**Demo data for users.** Any user with an empty account can choose Load demo data. They get about three years of Transactions, Budgets, Subscriptions and Goals in their own currency, and can remove exactly that data later.

**Scenario accounts for development.** A seed script creates fixed accounts, each proving a scenario: empty states, a student, a family, a freelancer at the Goals cap, a lapsed Premium user, yen, dinar, a stress account, and the golden dataset. Their data is generated by the same deterministic generator that makes demo data. Demo data is written in the user's own database context; scenario accounts are written through the system module.

## 1. User stories

- As a new user, I want to load realistic sample data, so that I can explore the dashboard, Budgets and charts before entering my own.
- As a user who loaded demo data, I want to remove exactly that data and keep anything I added myself.
- As a developer, I want named accounts that each show one scenario, so that I can test and demo without setting it up by hand.
- As a developer, I want the same data every time for the same account and date, so that tests and screenshots are reproducible.
- As a developer, I want an account with 100,000 Transactions, so that I can measure performance.

## 3. Concepts and fields

**Demo flag (D-219).** A boolean `demo` on Transactions, Budgets, Subscriptions and Goals. It is true only for rows created by Load demo data, and for charges that catch-up later creates from a demo Subscription. Scenario-account rows are the account's own data and have `demo` false.

**The generator.** A pure function in `shared/demo`. It takes the inputs below and returns rows, without reading the database or the clock.

| Input | Meaning |
| --- | --- |
| `persona` | `india` or `global` |
| `currency` | The profile currency; selects the scale (table below) |
| `timezone` | The profile zone, for local dates and times |
| `seed` | Bytes for the random generator |
| `now` | The instant generation ends; no row is later |
| `months` | Number of whole months before the current month, which is also included |
| `modifiers` | Count and amount multipliers and pattern overrides, for scenario accounts |

**Randomness.** The generator uses xoshiro128\*\*, seeded with the first 16 bytes of SHA-256 of:
- `demo:<userId>:<Idempotency-Key of the load request>` for demo data. Every load gets a new seed, so ids never repeat across loads (BR-F15-14).
- `scenario:<name>` for a scenario account.

Every random choice comes from this generator in a fixed order (BR-F15-15).

**Ids** come from a second, separate generator, seeded with the first 16 bytes of SHA-256 of `ids:` followed by the seed.
- **The bits:** each row takes 74 bits from it, in the order rows are written (BR-F15-15).
- **The id:** a UUIDv7 built from the row's `createdAt` and those bits.

Ids are therefore reproducible for a given seed, and taking them never shifts the amount draws.

**Month numbering.** Month 1 is the first generated month. The current month is month `months + 1` and is generated only up to `now`.

**Currency scale**

| Currency | Persona | Factor | Ranged step | Fixed step |
| --- | --- | --- | --- | --- |
| INR | India | 1/1 | ₹1 | ₹0.01 |
| USD | Global | 1/1 | 0.01 | 0.01 |
| EUR | Global | 9/10 | 0.01 | 0.01 |
| GBP | Global | 4/5 | 0.01 | 0.01 |
| JPY | Global | 150/1 | ¥10 | ¥1 |
| KWD | Global | 3/10 | 0.005 | 0.001 |

The factor multiplies every amount of the Global persona: ranges, fixed amounts, limits and targets. Factors and multipliers are fractions applied to integers in minor units, never floats (MON-1). A Global table amount `a`, in US cents, becomes `round(a × num × 10^e ÷ (den × 100))` in the target currency's minor units. Here `e` is that currency's exponent, and rounding is half away from zero (MON-7). India persona amounts are already in paise, with factor 1/1.
- **Rounding to steps:** a ranged bound is rounded to the ranged step; a fixed amount, limit or target to the fixed step.
- **Units inside rules** are amounts too, and scale with the factor: the 100.00 Vacation rounding becomes 90.00 in EUR, ¥15,000 in JPY and 30.000 in KWD.

## 4. Business rules

**Load demo data**

- **BR-F15-01** Load demo data is offered only while the account is empty: no Transactions, Budgets, Subscriptions or Goals (D-233). The portfolio does not count. It appears in three places:
    - the dashboard's onboarding panel (F08);
    - the empty Transactions list (F03);
    - Settings → Data.
- **BR-F15-02** It needs a connection and an empty write queue on this device ("Sync or discard 3 waiting changes first.").
- **BR-F15-03** The dialog says "Add about 3 years of sample Transactions, Budgets, Subscriptions and Goals in Indian rupee (INR)? You can remove all of it later in Settings → Data." with Cancel and Add demo data. While it runs, the button reads "Adding demo data…".
- **BR-F15-04** `POST /api/demo-data` runs one write transaction in the user's context (runtime role, RLS):
    1. Lock the profile row with `SELECT ... FOR UPDATE`. This serializes with every finance-row write (F03, BR-F03-05) and every catch-up run (JOB-2).
    2. Re-check that the account is empty. If not, return 409 `account_not_empty`.
    3. Generate with persona `india` for INR and `global` for every other currency, `months` 36, `now` as the request's instant (`ctx.now`), and seed `demo:<userId>:<Idempotency-Key>`.
    4. Insert in statements of at most 1,000 rows each, parents before children.
    5. Return 201 with the counts.
- **BR-F15-05** Every generated row has `demo` true. The generator also writes each demo Subscription's charges and tombstones for every due date up to today, so the next catch-up creates nothing until the next due date.
- **BR-F15-06** After success:
    - every query is invalidated;
    - the toast says "Demo data added.";
    - the currency becomes locked (F02, BR-F02-14).
- **BR-F15-07** A demo row stays demo when the user edits it (F03, BR-F03-18). A charge created later by catch-up copies its Subscription's `demo` flag (D-234).
- **BR-F15-08** While demo rows exist, the dashboard and the Transactions header show "Includes demo data · Remove", which links to Settings → Data.

**Remove demo data**

- **BR-F15-09** Remove demo data is offered while demo rows exist. It needs a connection and an empty write queue on this device.
- **BR-F15-10** The dialog states the counts from `GET /api/demo-data`: "Remove demo data? This deletes 4,312 demo Transactions, 6 Budgets, 10 Subscriptions and 4 Goals, including any changes you made to them. Transactions you added yourself stay."
    - **Own Goal Transactions:** when the user added Transactions to demo Goals, the dialog adds "It also deletes 2 Transactions you added to demo Goals."
    - **Buttons:** Cancel and Remove demo data.
- **BR-F15-11** `DELETE /api/demo-data` runs one write transaction, children before parents (P2, BR-P2-06):
    1. Lock the profile row with `SELECT ... FOR UPDATE`, as Load does. No Transaction write or catch-up run can then add a row in between.
    2. Delete non-demo Goal Transactions that point at demo Goals.
    3. Delete demo Transactions, which include every charge of a demo Subscription.
    4. Delete the tombstones of demo Subscriptions.
    5. Delete demo Subscriptions, Budgets and Goals.

    It returns 200 with the counts. A demo Transaction can never point at a non-demo Goal (F03, BR-F03-13; D-237), so removal never changes the user's own Goals.
- **BR-F15-12** After removal:
    - every query is invalidated;
    - the toast says "Demo data removed.";
    - the currency becomes editable again if no finance rows remain (F02, BR-F02-14).

**Status**

- **BR-F15-13** `GET /api/demo-data` returns three fields. Settings → Data, the onboarding panel and the empty list read it.
    - `present`: whether any demo row exists;
    - `accountEmpty`: per BR-F15-01;
    - `counts`: `{ transactions, budgets, subscriptions, goals, ownGoalTransactions }`.

**The generator**

- **BR-F15-14** The generator is deterministic. The same persona, currency, time zone, seed, `now` and modifiers always give identical rows, ids included. Two demo loads have different seeds (section 3), so their ids differ. A change queued on another device against an earlier load's row never touches a new row. An edit gets 404 and a new Goal Transaction gets `parent_missing`, both shown as rejected; a delete counts as done (D-239).
- **BR-F15-15** Each pattern in section 5 has a count rule and an amount rule.
    - **Count rules:**
        - "n to m" draws a whole count uniformly for each month;
        - "n a year" picks n months per calendar year without replacement;
        - "x% of months" makes a separate draw for each month.
    - **Days:** drawn with replacement, weighted. "Weekends ×1.5" gives Saturday and Sunday weight 1.5 and other days weight 1. "Weekdays ×1.5" gives Monday to Friday weight 1.5 and the weekend weight 1. "Weekdays only" excludes Saturday and Sunday.
    - **Times:** each row gets a time uniformly within its window, to the minute. With two windows, each is equally likely.
    - **Local to UTC:** local dates and times become `occurredAt` through the profile zone, with F03's daylight-saving rule (BR-F03-06).
    - **Draw order:**
        1. Before month 1, the birthday month.
        2. At the first generated month of each calendar year, that year's months for every "n a year" pattern, in table order.
        3. Then, for each month from 1 to `months + 1`, and for each pattern in table order (income first, then expenses), the month's count. For each row, in turn: day, time window, time, amount and payee, then the refund draw for a shopping row.

        Subscriptions, Budgets and Goals take no draws. Rows later than `now` are dropped after drawing, so a later `now` in the same month only adds rows.
    - **Drawing values:** every draw is a 32-bit integer `x`.
        - **Choices:** a choice among `m` options is `x mod m`.
        - **Weighted choices:** use the weights in tenths.
        - **Counts:** "n to m" is `n + x mod (m − n + 1)`; "40% of months" is `x mod 100 < 40`.
        - **Every row takes the same five draws:** day, time window, time, amount and payee, in that order, even when the pattern fixes one of them; a fixed value ignores its draw.
        - **A shopping row's refund draws:** chance (`x mod 100 < 4`), then, only if a refund follows: offset (`3 + x mod 13` days), full or partial (`x mod 10 < 7` is full), the share `p` (`20 + x mod 41`, only when partial), the time window and the time.
    - **Write order, for the id stream:**
        1. Budgets, Subscriptions and Goals, in table order.
        2. Transactions, in draw order.
        3. Charges and tombstones, by Subscription in table order, then by due date.
        4. Goal Transactions, by Goal in table order, then by date.
- **BR-F15-16** Amounts are scaled first (section 3), then drawn with integer arithmetic only.
    - **Ranged amounts:** with `n` steps between the scaled minimum and maximum, and `x` the next 32-bit draw, `k = (x × x × (n + 1)) >> 64`, computed with BigInt. This equals `floor(u² × (n + 1))` for `u = x ÷ 2^32`. It skews toward small amounts and is exact integer arithmetic, the same on every engine. The amount is the minimum plus `k` steps.
    - **Amount multipliers** are fractions applied to minor units, rounded half away from zero to the ranged step: scenario ×0.4 (2/5) and ×1.2 (6/5), seasonal ×1.4 (7/5), raises (108/100 and 103/100) and refund shares.
    - **Count multipliers** multiply the month's drawn count and round down: scenario ×0.8, ×1.4 and ×16, and seasonal ×1.8.
- **BR-F15-17** Every generated row satisfies F03 to F06:
    - payees and categories valid for the type;
    - every amount within MON-5;
    - no row later than `now`;
    - no Goal below zero at any instant;
    - no Goal Transaction after its Goal was completed or archived;
    - charges exactly on the TIME-9 schedule.

    The generator does not apply the 10-day entry window, which exempts system rows (TIME-7). Each Transaction's `createdAt` equals its `occurredAt`, and `updatedAt` equals `createdAt`. Parent rows get these `createdAt` values, at 00:00 local:
    - a Subscription: its start date;
    - a Budget: the first day of its first effective month;
    - a Goal: the first day of its creation month, plus one minute per Goal in table order. This defines the "oldest" order D-29 uses.

    **Nothing after `now` (D-271).** Persona events dated after `now` are never generated, which matters for accounts shorter than 36 months:
    - a Subscription stores the amount in force at `now`, and gets an end date only when its last charge is due on or before `now`;
    - tombstones exist only for dates on or before `now`;
    - a Goal whose completion or archive date is after `now` stays active, so `dinar`, a Free account, ends at the 3-Goal cap;
    - Budget changes after `now` are left out.
- **BR-F15-18** Refunds: each shopping expense (not the large purchase) has a 4% chance of a refund 3 to 15 days later, if that is not after `now`. The refund keeps the payee and category. Its amount is the full expense (70% of refunds), or `p` percent of it, where `p` is a whole number from 20 to 60, rounded half away from zero to the ranged step.
- **BR-F15-19** Raises: the India salary rises 8% each April, and the Global salary 3% each January, starting with the first one after month 1. Each raise is rounded to the fixed step.
- **BR-F15-20** Free users keep a free Goal slot: the demo set has 2 active Goals, 1 completed and 1 archived (D-234), within the Free cap of 3 active Goals (D-99).

**Scenario accounts**

- **BR-F15-21** `npm run db:seed` runs five steps:
    1. From M3, run price catch-up (F07, BR-F07-02), so stored prices cover every seeded trade before the accounts are used. The asset catalog comes from migrations.
    2. Create each missing scenario account.
    3. Skip accounts that already exist.
    4. Print each account's email, plan and row counts.
    5. Print the shared password.

    Options:

    | Option | Effect |
    | --- | --- |
    | `--reset` | Deletes and recreates the scenario accounts. It touches only emails ending in `@daybook.test`, and first deletes each account's Stripe Customer, if any (F12, BR-F12-26). It ends with "Restart the dev server so it forgets its catch-up notes." |
    | `--only <name,...>` | Limits the run to the named accounts |
    | `--today YYYY-MM-DD` | Generates as if that were today. It must not be later than the real date |
    | `--golden` | Also creates the golden account (BR-F15-26) |

- **BR-F15-22** Each account is created in four steps:
    1. **Auth user and password:** through Better Auth's internal adapter (`auth.$context`, as in F01, BR-F01-28), with no breached-password call and no rate limit.
    2. **App rows:** profile, finance rows, entitlements and plan status, through the system module (P2, BR-P2-26), in statements of at most 1,000 rows.
    3. **Portfolio:** from M3, F07 seeds it, as onboarding would. The golden account gets the fixture instead (BR-F15-26).
    4. **`lastCatchUpOn`:** set to the seed day.
- **BR-F15-23** Every scenario account uses the password `daybook-scenario-password`. It is public through the repository (SEC-13); the accounts hold generated data only.
- **BR-F15-24** Scenario data ends at the moment the seed runs. Afterwards only Subscription charges continue, through catch-up. Run `--reset` to refresh.
- **BR-F15-25** Seeded Premium (D-156, BR-P4-16) writes three things:
    - every `premium` and `limit` code as an entitlement key with source `seed`;
    - a plan record as F12 defines it (BR-F12-27);
    - no Stripe Customer. The billing page shows "Premium was granted by the seed script, so there is nothing to manage in Stripe." (F12). If the account buys Premium, its first sync replaces the seeded state (F12, BR-F12-05 and BR-F12-11).

    For `lapsed`, the seed writes an `ended` plan record and no entitlements (F12, BR-F12-27). Locks are computed, not stored (F06, BR-F06-12), so its 2 newest Goals are locked with nothing more to write.
- **BR-F15-26** `--golden` creates `golden@daybook.test` from the fixture module `seed/golden.ts`, which encodes [03-golden-dataset.md](../03-golden-dataset.md) row for row. Integration tests use the same module.
    - **Rows:** profile, Budgets, Subscriptions, Goals, the Cult Gym tombstone, and Transactions #1 to #26. From M3, also the fixture asset `golden-mix`, its three prices and golden's two trades (F07, BR-F07-17). From M4, Premium (BR-F15-25).
    - **Row 27 and catch-up:** row 27 is left out and `lastCatchUpOn` is 2026-10-31, so the first request on 2026-11-02 creates row 27 (due 1 November) through catch-up, as the dataset says.
    - **Date guard:** the script refuses `--golden` before 2026-11-02 with "The golden dataset runs to 2 Nov 2026; seed it on or after that date." Tests run it with the frozen clock, which every business date in SQL comes from (P2, BR-P2-43).
    - **Once per database:** the fixture's ids are fixed, so it loads at most once per database. `--golden` does nothing when the golden account exists, unless `--reset` is given.
    - **In tests (D-245):** the fixture is built once into a template database. Each test file that changes golden data, or writes it from two sessions, runs in its own copy, made with `CREATE DATABASE ... TEMPLATE`, and first clears the catch-up note (P2, BR-P2-14).
- **BR-F15-27** The stress account's generator output is cut to exactly 100,000 Transactions by dropping the oldest before anything is inserted. Its Subscriptions and Goal schedules start 12 months late, and the cut falls inside the first 12 months (about 3 to 4 months are dropped). So the cut removes only plain income and expenses:
    - no Goal loses a contribution;
    - no Subscription loses a charge that catch-up would then recreate.

## 7. Flows

**7.1 Load demo data**

1. A user with an empty account chooses Load demo data from the onboarding panel.
2. The dialog explains the currency and how to remove the data; they confirm.
3. `POST /api/demo-data`.
4. **409 `account_not_empty`:** "Your account already has data, so demo data can't be added. Remove it first, or reset your data in Settings → Data." The status refetches.
5. **201:** BR-F15-06. The dashboard renders three years of data, with Budget, Subscription and Goal widgets populated.

**7.2 Remove demo data**

1. In Settings → Data the user chooses Remove demo data. The dialog shows the counts.
2. They confirm. `DELETE /api/demo-data`.
3. **200:** BR-F15-12. The user's own Transactions remain.

**7.3 Seed the scenario accounts**

1. Run `npm run db:seed`.
2. The script creates the eight accounts. From M3 it seeds each portfolio; from M4 it seeds Premium states.
3. It prints the account table and the password.
4. Log in as `lapsed@daybook.test` to see two locked Goals.

**7.4 Golden in tests**

1. An integration test loads `seed/golden.ts` into the CI database with the frozen clock (TST-3).
2. The first request runs catch-up and creates row 27.
3. Every golden assertion runs.

## 9. Plan gating

None. Demo data never grants Premium, and keeps a Free user under the Goals cap (BR-F15-20).

## 10. Offline behavior

Load and remove need a connection and an empty queue on this device (BR-F15-02, BR-F15-09). After a load or removal, cached queries are invalidated; a device that was offline refetches when it reconnects.

## 13. Edge cases

- **Load from two tabs at once:** the profile lock serializes them. The second returns 409 `account_not_empty`.
- **Another device creates a Transaction during a load:** the lock serializes them. Either the create lands first and the load returns 409, or the load lands first and the create succeeds as the user's own row.
- **The user edits a demo Budget:** it stays demo and is removed with the rest.
- **The user adds their own Budget** for a category without a demo Budget: it is not demo and stays after removal.
- **The user adds a contribution to a demo Goal:** removal deletes it too, and the dialog says so (BR-F15-10).
- **Load, remove and load again:** the second load has a new seed, so new ids and different rows. Changes queued on another device against the first load's rows never touch the new ones. Edits get 404 and new Goal Transactions get `parent_missing`, both rejected there; deletes count as done.
- **A load near midnight:** `now` is the request's instant, so the current month includes rows up to that minute and none later.
- **Daylight-saving zones:** times inside a spring-forward gap move forward, so generated rows never hold an impossible local time.
- **Scaling to KWD:** ranged amounts are multiples of 5 fils, so their `amountMinor` is a multiple of 5.
- **Scaling to JPY:** ranged amounts are multiples of ¥10.
- **Running `db:seed` twice:** the second run creates nothing and prints the same table.
- **`--reset` on a database with real users:** only `@daybook.test` accounts are touched.

## 14. Acceptance criteria

- **AC-F15-01** (unit) The generator, run twice with the same inputs, returns byte-identical rows, and no generator module calls `Math.exp`, `Math.log` or `Math.pow`. With a different seed it returns a different set.
- **AC-F15-02** (unit, M2) For the India and Global personas with `months` 36, every Transaction count is between 4,000 and 9,000.
- **AC-F15-03** (unit) Generated data meets BR-F15-17:
    - every row passes F03's Zod schemas;
    - no Goal's running progress is ever negative;
    - no Goal Transaction is dated after its Goal was completed or archived;
    - charge dates match the TIME-9 schedule;
    - no row is later than `now`.
- **AC-F15-04** (unit) Scaling:
    - JPY ranged amounts are multiples of 10 minor units;
    - KWD ranged amounts are multiples of 5;
    - the completed Goal's contributions sum exactly to its target in every currency.
- **AC-F15-05** (integration) Load demo data on an empty INR account creates rows with `demo` true and returns the counts. The next catch-up creates no charge dated today or earlier.
- **AC-F15-06** (integration) Load demo data on an account with one Budget returns 409 `account_not_empty` and changes nothing.
- **AC-F15-07** (integration, M2) After a load, the user adds one manual expense and one contribution to the demo Vacation Goal. Remove demo data then:
    - deletes every demo row and that contribution;
    - keeps the manual expense;
    - reports `ownGoalTransactions: 1`.
- **AC-F15-08** (integration) After removing demo data from an account with no other finance rows, `currencyEditable` is true.
- **AC-F15-09** (integration, M2) A charge created by catch-up for a demo Subscription has `demo` true and is removed by Remove demo data.
- **AC-F15-10** (integration, M2) The 2 active Goals of a Free user's demo data leave `goals.active.max` headroom of 1.
- **AC-F15-11** (integration; plans from M4) `db:seed` on an empty database creates the eight accounts with the plans in section 5. A second run creates nothing. `--reset --only dinar` recreates only `dinar@daybook.test`.
- **AC-F15-12** (integration, M2) The stress account has exactly 100,000 Transactions.
    - Its oldest Transaction is dated in month 12 or earlier, so the cut stayed inside the first 12 months.
    - Every charge from month 13 onward is present.
    - A catch-up run right after seeding creates no charge for a past date.
- **AC-F15-13** (integration, M2) `seed/golden.ts` with the frozen clock reproduces every figure in [03-golden-dataset.md](../03-golden-dataset.md). Row 27 appears after the first request's catch-up.
- **AC-F15-14** (E2E, M3) Logged in as `new@daybook.test`, a user loads demo data from the onboarding panel, sees the dashboard populated, then removes it from Settings → Data and sees the onboarding panel again.
- **AC-F15-15** (performance) Loading demo data completes within 10 seconds against a warm Neon database.
- **AC-F15-16** (integration) Two loads on the same account, with a removal in between, share no Transaction id.
- **AC-F15-17** (integration, M2) Removal and a concurrent contribution to a demo Goal from another session serialize on the profile lock. Either the contribution is counted and deleted, or it fails with `parent_missing`; removal never fails with `has_dependents`.
- **AC-F15-18** (integration, M2) Every scenario account passes BR-F15-17's checks, including "nothing after `now`", right after `db:seed`.
